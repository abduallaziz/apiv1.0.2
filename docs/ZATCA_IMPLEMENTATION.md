---

## 1. Scope & applicability

ZATCA e-invoicing is part of the **VAT system**: it applies **only to VAT-registered businesses**.
A tenant with **no VAT number is outside ZATCA entirely** — it sells with an ordinary receipt, no
device, no OTP, no fields. ZATCA only engages for a tenant that has a VAT number and an onboarded
device on the selling branch.

Two invoice families:
- **Simplified (B2C, `0200000`)** — default; REPORTED to ZATCA within 24h.
- **Standard (B2B, `0100000`)** — when the buyer has a VAT number; CLEARED (pre-approved).
- Plus credit notes (`381`) and debit notes (`383`).

## 2. Feature flags & secrets (env)

| Variable | Meaning | Default |
|---|---|---|
| `ZATCA_ENABLED` | Issue signed documents inside each pooled sale | `false` |
| `ZATCA_GATEWAY` | `null` = documents wait as pending; `fatoora` = really talk to ZATCA | `null` |
| `ZATCA_KEY_ENC_KEY` | **Our** AES-256-GCM master key (32 bytes, base64/hex) encrypting device private keys + CSID secrets at rest. **Not a ZATCA credential.** Must stay stable or stored keys become unreadable. | — |

With `ZATCA_ENABLED=false` nothing changes in the sale path. The module routes are always mounted.

## 5. The chain: ICV + PIH

Each **device** (per branch) owns one gap-free counter (ICV) and one hash chain (PIH). Issuance
locks the device row `FOR UPDATE`, so a branch's documents are strictly ordered and a rolled-back
sale rolls back the counter with it. First PIH = base64 of the hex text of `sha256("0")`
(`ZATCA_FIRST_PIH`). Each document's SHA-256 hash becomes the next document's PIH.

## 6. Onboarding flow

```
create device (seller data)  →  generate CSR (device keypair, private key encrypted)
  →  onboard: OTP → Compliance CSID (POST /compliance)
  →  compliance checks (invoice + credit + debit all PASS)
  →  [production only] activate → Production CSID (POST /production/csids)
```

- **Sandbox** uses the public OTP `123456` and has **only** the compliance endpoint. A sandbox device
  therefore **stays on the compliance CSID** and goes live right after the compliance checks —
  "activate production" is **blocked** for sandbox (the compliance endpoint rejects production
  credentials with HTTP 401; that was the demo "error" bug).
- **Simulation / production** need an OTP generated by the taxpayer on the Fatoora portal, then
  compliance checks, then the production CSID.

Endpoints (prefix `/api/v1`, all tenant-scoped, `settings.manage`):
`POST /zatca/devices`, `POST /zatca/devices/:id/csr`, `POST /zatca/devices/:id/onboard {otp}`,
`POST /zatca/devices/:id/compliance-checks`, `POST /zatca/devices/:id/activate`,
`DELETE /zatca/devices/:id`, `GET /zatca/devices`, `GET /zatca/invoices`, `POST /zatca/flush`.

Gateway base URLs (`https://gw-fatoora.zatca.gov.sa/e-invoicing/{path}`): sandbox=`developer-portal`,
simulation=`simulation`, production=`core`.

## 7. Issuance & sending

- **At sale time** (inside the tx, when `ZATCA_ENABLED` and the branch has a usable device): the
  document is built, signed, chained and stored as `pending`. A branch with no device → no-op.
- **Sending**: `POST /zatca/flush` sends pending documents per device in ICV order, stopping at the
  first that doesn't go through. Sandbox → compliance-check (PASS = reported). Simulation/production
  → reporting (simplified) or clearance (standard). Status: `pending → reported|cleared|rejected|error`.

## 8. Document rules proven against the real ZATCA validator

These four were found ONLY by submitting to the sandbox (unit tests pass regardless):

1. **`AccountingCustomerParty` is mandatory** in the XSD even for a nameless walk-in simplified
   invoice → always emitted (empty `<cac:Party></cac:Party>` when no buyer).
2. **QR tags 6 (hash) and 7 (signature) are base64 TEXT**, not raw bytes — the validator compares
   them as text against the signed XML's base64 values.
3. **QR timestamp is the real UTC instant** (`issue_at`), reconciling with the KSA-local
   IssueDate/IssueTime (rule KSA-25). A KSA-local `...Z` string fails the check.
4. **Standard (B2B) invoices carry the supply date** `cac:Delivery/cbc:ActualDeliveryDate`
   (rule BR-KSA-15). Simplified invoices do not.

VAT categories: `S` standard (needs rate > 0), `Z` zero-rated, `E` exempt, `O` out-of-scope. Z/E/O
emit `Percent` 0 with a `TaxExemptionReasonCode` (VATEX-SA-…) + `TaxExemptionReason` in both the tax
subtotal and each line. All four PASS the sandbox.

## 9. Operations runbook

### Register a sandbox device (demo)
1. Settings → الفوترة الإلكترونية → إضافة جهاز فوترة. Env **تجريبي (sandbox)**, test seller data,
   VAT `300000000000003`.
2. Save → توليد CSR → OTP `123456` → طلب شهادة الامتثال → تشغيل فحوصات الامتثال.
3. Device becomes **مفعّل** immediately (no production step on sandbox).
4. Make a sale → طابور الإرسال → إرسال الآن → status should be **أُبلغ** (reported).

### Troubleshooting
- **Send shows "خطأ" (error), not "مرفوض"**: credentials/transport, not the document. On sandbox the
  usual cause was a device activated to production (compliance endpoint returns 401 for production
  creds). Fix: delete the device and re-create; sandbox now never activates to production.
- **"مرفوض" (rejected)**: the document failed validation — read `last_error`/the queue response for
  the ZATCA message and fix the builder.
- **Nothing in the queue after a sale**: the selling branch has no device, or `ZATCA_ENABLED` is off,
  or the sale wasn't on the device's branch (one device per branch).

## 10. Decisions

- **One device per branch** (final): independent ICV/PIH chain per branch → concurrent invoicing +
  isolation; a single-branch business sees no extra onboarding.
- **Invisible onboarding (PAUSED)**: the goal is ZATCA invisible to the seller (like Rewaa). Because
  ZATCA only applies to VAT-registered tenants, the design is to **gate activation on the tenant
  having a VAT number**, auto-create the device from the profile, do the one-time authorization in
  onboarding/operations (not the seller UI), auto-send on a schedule, and hide the screen. Paused
  until the owner has full details.
